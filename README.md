## 1. ฝั่งฮาร์ดแวร์ (Arduino Uno + HC-05)

### การต่อสาย

| Arduino Uno | ต่อไปที่ | หมายเหตุ |
|---|---|---|
| **D2** | Pulse OUT ของบอร์ดหัววัด GM | ต้องเป็น D2 หรือ D3 เท่านั้น (INT0/INT1) |
| D10 (RX) | HC-05 **TXD** | ต่อตรงได้ (3.3V เข้า Uno ถือเป็น HIGH) |
| D11 (TX) | HC-05 **RXD** | **ต้องผ่าน voltage divider** R1=1kΩ, R2=2kΩ ลง GND |
| D8 | Buzzer / LED ติ๊ก | ผ่าน R 220Ω (ตัวเลือก) |
| D9 | LED เตือนสีแดง | ผ่าน R 220Ω (ตัวเลือก) |
| 5V | VCC ของ HC-05 | HC-05 module ทั่วไปมี regulator บนบอร์ด |
| GND | GND ร่วมกันทุกตัว | **ต้องต่อ GND ร่วมกัน** ไม่งั้นนับพัลส์เพี้ยน |

```
   GM Tube board                Arduino Uno                  HC-05
 ┌──────────────┐            ┌───────────────┐          ┌───────────┐
 │  HV 400V     │            │               │          │           │
 │  Pulse OUT ──┼────────────┤ D2 (INT0)     │          │           │
 │  VCC (5V) ───┼──── 5V ────┤ 5V        D10 ├──────────┤ TXD       │
 │  GND ────────┼──── GND ───┤ GND       D11 ├──1kΩ──┬──┤ RXD       │
 └──────────────┘            │               │       │  │           │
                             │           GND ├───────┴──┤ GND (2kΩ) │
                             └───────────────┘   2kΩ    └───────────┘
```

> **เรื่องความปลอดภัย:** บอร์ดหัววัด GM สร้างไฟ 400–500 VDC ห้ามจับตัวเก็บประจุ HV ขณะจ่ายไฟ และให้คายประจุก่อนถอดหลอดเสมอ

### การตั้งค่าใน sketch

แก้ค่าคงที่ในไฟล์ `telepole_gm.ino` ให้ตรงกับหลอดที่ใช้:

```cpp
const float CPM_PER_USV_H = 108.0f;   // LND 712 (ค่าที่เครื่องนี้ใช้)
// J305 / M4011 ใช้ 153.8 · SBM-20 ใช้ 150.5
const float ALARM_USV_H   = 2.5f;     // LED เตือนที่ตัวเครื่อง
```

> ใช้บอร์ด **Arduino Uno R3** ซึ่งเป็น ATmega328P ตัวเดียวกับ Nano
> ขาที่ใช้จึงเหมือนกันทุกขา ต่างกันแค่รูปทรงบอร์ดกับหัวเสียบ USB
> ตอนคอมไพล์เลือก **Tools → Board → Arduino Uno**

### หลอด LND 712 กับค่า sensitivity

`CPM_PER_USV_H` คือค่าเดียวที่ใช้แปลง CPM เป็น uSv/h — แก้ได้ 2 ที่:

| แก้ที่ไหน | ผลกับอะไร | ต้อง flash ใหม่ไหม |
|---|---|---|
| `CPM_PER_USV_H` ใน `telepole_gm.ino` | ค่า uSv/h ในช่อง CSV และ LED เตือนที่ตัวเครื่อง | **ต้อง** |
| เมนูสอบเทียบในแอป (ไอคอนเฟือง) | ทุกตัวเลขที่แสดงบนมือถือ | ไม่ต้อง |

**แอปไม่ได้ใช้ค่า uSv/h ที่บอร์ดส่งมา** แต่คำนวณใหม่เองจาก CPM
เพราะฉะนั้นเวลาสอบเทียบจริงให้แก้ในแอปอย่างเดียวพอ ค่าใน firmware มีไว้ให้ LED
ที่ตัวเครื่องเตือนได้ถูกต้องเท่านั้น

ที่มาของเลข 108: datasheet ของ LND 712 ระบุ gamma sensitivity **18 CPS ต่อ 1 mR/h**
(อ้างอิง Co-60) — 18 CPS = 1080 CPM และ 1 mR/h ≈ 10 uSv/h จึงได้ **108 CPM ต่อ 1 uSv/h**

ข้อควรรู้: 108 เป็นค่าจาก datasheet ที่พลังงานอ้างอิงจุดเดียว ไม่ใช่ค่าที่สอบเทียบแล้ว
หลอด GM ตอบสนองต่างกันตามพลังงานโฟตอน ค่า uSv/h ที่ได้จึงเป็น "ค่าเทียบเท่า"
**CPM คือค่าที่วัดได้จริง** ถ้าต้องการค่า uSv/h ที่เชื่อถือได้ ต้องเทียบกับเครื่องมาตรฐาน
แล้วกรอกค่าที่ได้ลงเมนูสอบเทียบในแอป

LND 712 เป็นหลอดหน้าต่างไมกาบาง (1.5–2.0 mg/cm²) จึงรับอัลฟา/บีตาได้ด้วย
ค่า uSv/h ใช้ได้เฉพาะกับรังสีแกมมา ถ้าเอาไปจ่ออัลฟา/บีตา ให้อ่าน **CPM เท่านั้น**

**ค่านี้สำคัญที่สุดต่อความถูกต้อง** — ถ้าใส่ผิด ค่า µSv/h จะผิดทั้งหมด ค่าที่ให้มาเป็นค่า sensitivity สำหรับ Cs-137 จาก datasheet ถ้าต้องการความแม่นจริงควรสอบเทียบกับเครื่องมาตรฐาน

### วิธีคำนวณ

- **CPM** ใช้ rolling window 60 วินาที (อาเรย์ 60 ช่อง ช่องละ 1 วินาที) → ค่านิ่ง ไม่กระโดดเหมือนการนับสด และช่วง 60 วินาทีแรกจะ scale ตามจำนวนวินาทีที่เก็บได้ เพื่อให้มีตัวเลขใช้งานทันที
- **Dose rate** = `CPM / CPM_PER_USV_H`
- **Accumulated** = อินทิเกรตทีละวินาที `µSv += µSv/h × (Δt_ms / 3,600,000)`
- ISR มี **debounce 190 µs** ตาม dead time ของหลอด GM เพื่อไม่ให้นับ ringing ซ้ำเป็นหลายพัลส์
- อ่าน/เคลียร์ตัวนับด้วย `noInterrupts()` เพื่อกัน race condition กับ ISR

### รูปแบบข้อมูลที่ส่งออก (ทุก 1 วินาที)


```
34.0,0.2210,0.0031,1
```
คือ `CPM,uSv_h,Accumulated_uSv,CPS` — บรรทัดที่ขึ้นต้นด้วย `#` เป็น comment/ACK ฝั่งแอปจะข้ามให้

**ช่อง CPS** คือจำนวนพัลส์ดิบของวินาทีที่เพิ่งผ่านไป ไม่ผ่านการเฉลี่ย ต่างจาก CPM ที่เฉลี่ยมา
60 วินาที ใช้สองอย่าง: แสดงค่าที่ตอบสนองทันทีตอนกวาดหาจุดร้อน และขับเสียงคลิกในแอป

ช่องนี้เพิ่มมาทีหลัง แอปจึงถือเป็นช่องเสริม — firmware รุ่นเก่าที่ส่งมาแค่ 3 ช่องยังใช้ได้ตามปกติ

### คำสั่งที่รับจากแอป

| คำสั่ง | ผล |
|---|---|
| `R` | รีเซ็ตค่าสะสม |
| `Z` | รีเซ็ตค่าสะสม + ล้างหน้าต่างเฉลี่ย CPM |
| `?` | ส่งข้อมูลรอบใหม่ทันที |

### อัปโหลด

1. Arduino IDE → Board: **Arduino Nano**, Processor: **ATmega328P (Old Bootloader)** ถ้าเป็นบอร์ดจีน
2. **ถอดสาย HC-05 ออกจาก D10/D11 ก่อนอัปโหลด** ไม่งั้นอัปโหลดไม่ผ่าน (ในโค้ดนี้ใช้ SoftwareSerial จึงมักไม่ชน แต่ถอดไว้ปลอดภัยกว่า)
3. เปิด Serial Monitor 9600 baud เพื่อดูข้อมูลชุดเดียวกับที่ส่งออกบลูทูธ

### จับคู่ HC-05

โมดูลมาจากโรงงานที่ baud **9600**, PIN **1234** หรือ **0000** — ถ้าอยากเปลี่ยนชื่อให้จำง่าย เข้า AT mode (กดปุ่มบนโมดูลค้างตอนจ่ายไฟ, baud 38400) แล้วสั่ง:

```
AT+NAME=TELEPOLE
AT+PSWD=1234
AT+UART=9600,0,0
```

## 2. บอร์ดที่ใช้จริงในโปรเจกต์นี้

จากรูปบอร์ด: เป็นโมดูล GM counter สำเร็จรูป (PCB แดง) ไม่ใช่วงจรทำมือ

| จุด | รายละเอียด |
|---|---|
| หลอด GM | **LND 712** — หน้าต่างไมกาบาง 1.5-2.0 mg/cm² รับได้ทั้งอัลฟา บีตา แกมมา |
| IC หลัก | **CD4093BM** (TI) — quad 2-input NAND Schmitt trigger ทำหน้าที่จัดรูปพัลส์ |
| ไฟเลี้ยง | **5V** |
| ขั้ว `GM` (บนสุด) | ต่อหลอด GM |
| ขั้วข้างทริมพอตสีฟ้า | ไฟเลี้ยง 5V / GND |
| ขั้ว `CN1` (ล่างขวา) | **พัลส์ออก** |
| `P1` ทริมพอตสีฟ้า `503` = 50kΩ | ปรับแรงดัน HV — **ห้ามหมุน** ถูกตั้งบน plateau ไว้แล้ว |

**เพราะมี CD4093 อยู่แล้ว พัลส์ที่ออกจาก CN1 เป็นระดับลอจิก 0–5V ต่อเข้า D2 ได้โดยตรง**
ไม่ต้องสร้างวงจร transistor/optocoupler คั่นตามหัวข้อ 1.5 (หัวข้อนั้นเก็บไว้เผื่อกรณีที่ต้องต่อ
กับหัววัดที่ไม่มีภาคจัดรูปสัญญาณ)

ก่อนเสียบ D2 ให้ยืนยันว่าขาไหนของ CN1 เป็นสัญญาณ ขาไหนเป็น GND:
จ่ายไฟ 5V แล้ววัดเทียบ GND ของบอร์ด — ขาที่ต่อถึง GND คือกราวด์
ส่วนอีกขาถ้านิ่งที่ ~5V แปลว่าพัลส์เป็นขาลง ตรงกับ `PULSE_EDGE = FALLING` ที่ตั้งไว้แล้ว

สายจาก CN1 ไป D2 ให้สั้นที่สุด เพราะภาคสร้าง HV บนบอร์ดเป็น switching converter
สัญญาณรบกวนแรง สายยาวจะทำให้นับเกิน

### เช็คว่าค่าที่อ่านได้สมเหตุสมผลไหม

เปิดเครื่องทิ้งไว้ในห้องปกติสัก 5 นาที ค่าควรอยู่ราว **10-30 CPM**

ตัวเลขนี้มาจากรังสีพื้นหลังธรรมชาติ 0.05-0.20 uSv/h คูณกับค่าของ LND 712 ที่ 108 CPM ต่อ 1 uSv/h
ได้ประมาณ 5-22 CPM บวกความกระเพื่อมแบบปัวซง

| อาการ | สาเหตุที่น่าสงสัย |
|---|---|
| 0 CPM ตลอด | ขั้วพัลส์ผิด (เปลี่ยน `PULSE_EDGE` เป็น `RISING`) / บอร์ดไม่ได้จ่ายไฟ / ต่อผิดขา |
| หลักพัน CPM ตอนไม่มีแหล่งกำเนิด | สัญญาณรบกวนจากภาค HV — สายยาวเกินไป, GND ไม่ร่วม, สายไม่ชีลด์ |
| ค่ากระโดดตอนขยับก้าน | สายหลวม / ไฟฟ้าสถิต |

### ค่า uSv/h ยังควรสอบเทียบเอง

หลอด LND 712 มีค่าจาก datasheet อยู่แล้ว (108 CPM ต่อ 1 uSv/h — ที่มาดูหัวข้อ 1)
ทั้ง firmware และแอปจึงตั้งค่านี้ไว้เป็นค่าเริ่มต้น ใช้ได้เลยโดยไม่ต้องทำอะไรเพิ่ม

แต่ค่า datasheet วัดที่พลังงานอ้างอิงจุดเดียวและวัดกับหลอดใหม่ ของจริงยังต่างได้จาก
อายุหลอด แรงดัน HV ที่ตั้งไว้ และภาชนะ/ฝาครอบที่กั้นอยู่ ถ้าต้องการตัวเลขที่อ้างอิงได้ในรายงาน
ยังต้องสอบเทียบกับเครื่องมาตรฐานอยู่ดี

แอปมีเมนู **สอบเทียบภาคสนาม** (ไอคอนเฟืองบน dashboard): วางหัววัดข้างเครื่องมาตรฐาน
รอค่านิ่ง กรอกค่าที่เครื่องมาตรฐานอ่านได้ แล้วแอปคำนวณให้เอง — ไม่ต้อง flash บอร์ดใหม่
เพราะแอปคำนวณ uSv/h และค่าสะสมเองจากค่า CPM ที่รับมา

ถ้ายังไม่ได้สอบเทียบ ให้ดู **CPM อย่างเดียว** ซึ่งเป็นค่าที่หลอดวัดได้จริง
ใช้เปรียบเทียบและหาจุดร้อนได้ทันทีโดยไม่ต้องพึ่งค่าสอบเทียบ

## 3. ฝั่งแอป Android (Flutter)

### ติดตั้ง

```bash
cd app
flutter create .          # สร้าง android/ ios/ ที่ยังไม่มีในโฟลเดอร์นี้
flutter pub get
```

จากนั้น:

1. เปิด `android/app/src/main/AndroidManifest.xml` แล้ววาง permission จาก `android_manifest_snippet.xml`
2. ตั้ง `minSdkVersion 21` ใน `android/app/build.gradle`
3. `flutter run`

ไฟล์เสียงเตือน `app/assets/alarm.wav` มีอยู่ในรีโปแล้ว สร้างจาก `tool/make_sounds.py`
อยากเปลี่ยนเสียงดูวิธีใน `app/assets/README.md`

### แพ็กเกจที่ใช้

| แพ็กเกจ | หน้าที่ |
|---|---|
| `flutter_blue_classic` | Bluetooth **Classic (SPP)** — HC-05 ใช้ SPP ไม่ใช่ BLE จึงใช้ `flutter_blue_plus` ไม่ได้ |
| `permission_handler` | ขอสิทธิ์ BLUETOOTH_CONNECT/SCAN (Android 12+) และ location (ต่ำกว่า) |
| `fl_chart` | กราฟเส้น real-time |
| `vibration` | สั่นเตือน |
| `audioplayers` | เสียงเตือน |
| `path_provider` | หาที่เก็บไฟล์บันทึกการสำรวจ |
| `share_plus` | ส่งออกไฟล์ CSV เข้าแอปอื่น |

### สถาปัตยกรรม

```
ScanScreen ──เลือกอุปกรณ์──▶ TelepoleConnection (ChangeNotifier)
                                    │  byte stream → buffer → split('\n')
                                    │  → Reading.tryParse() → history (300 จุด)
                                    ▼
                            DashboardScreen ──▶ AlarmService (สั่น/เสียง)
                                    ├──────────▶ TrendChart (5 นาทีล่าสุด)
                                    └──────────▶ SessionRecorder ──▶ ไฟล์ CSV
                                                        │
                                    SessionsScreen ◀────┘
                                            └──▶ SessionDetailScreen ──▶ SessionChart
```

จุดที่ต้องระวังและโค้ดจัดการไว้แล้ว:

- **ข้อมูลมาเป็น chunk ไม่ตรงขอบบรรทัด** → เก็บ `_rxBuffer` แล้วตัดที่ `\n` เท่านั้น ท่อนท้ายที่ยังไม่จบบรรทัดเก็บไว้รอบถัดไป
- **ข้อมูลขยะตอนเชื่อมต่อครั้งแรก** → `Reading.tryParse()` คืน `null` แทนที่จะ throw ทำให้ stream ไม่ล้ม
- **บัฟเฟอร์บวม** ถ้าอุปกรณ์ส่งข้อมูลไม่มี newline → ตัดทิ้งเมื่อเกิน 4 KB
- **เสียงเตือนซ้อนกัน** → `AlarmService.update()` เริ่ม/หยุดเฉพาะตอนระดับ *เปลี่ยน* เรียกทุกวินาทีได้ปลอดภัย

### ระดับเตือนภัย (ปรับได้ในแอปผ่านไอคอน ⚙)

| ระดับ | ค่าเริ่มต้น | UI | เสียง/สั่น |
|---|---|---|---|
| ปกติ | < 0.5 µSv/h | เขียว | ไม่มี |
| เฝ้าระวัง | ≥ 0.5 µSv/h | เหลือง + แถบเตือน | สั่นทุก 2 วินาที |
| เกินเกณฑ์ | ≥ 2.5 µSv/h | แดง ทั้งพื้นหลังและตัวเลข | สั่นเป็นจังหวะ + เสียง ทุก 0.7 วินาที |

> ค่าอ้างอิง: รังสีพื้นหลังธรรมชาติทั่วไปอยู่ราว **0.05–0.20 µSv/h** ถ้าอ่านได้สูงกว่านี้มากตอนไม่มีแหล่งกำเนิด ให้สงสัยการต่อสาย/สัญญาณรบกวนก่อนสรุปว่าเจอรังสีจริง

## 4. การทดสอบโดยไม่มีหัววัด

### วิธีที่ง่ายที่สุด: โหมดสาธิตในแอป

ในหน้า Scan มีปุ่ม **โหมดสาธิต** — กดแล้วแอปจะสร้างข้อมูลปลอมขึ้นมาเองโดยไม่ต้องต่อบลูทูธ
มีสไลเดอร์ปรับระดับ 0-800 CPM เพื่อทดสอบว่าแถบเตือน เสียง และการบันทึกทำงานถูกต้อง

ข้อมูลจำลองเดินผ่านโค้ดเส้นทางเดียวกับข้อมูลจริงทุกขั้นตอน (อินทิเกรตค่าสะสม เข้ากราฟ เข้าไฟล์บันทึก)
สิ่งที่เห็นบนจอจึงสะท้อนพฤติกรรมจริง ไม่ใช่หน้าจอปลอมที่แยกออกมาต่างหาก
ค่าที่สร้างใช้การแจกแจงปัวซงตามฟิสิกส์ของการสลายตัว ตัวเลขจึงกระเพื่อมเหมือนของจริง

### วิธีทดสอบฝั่ง firmware: ป้อนพัลส์ปลอมเข้า D2

ต่อสาย jumper จาก D3 ไป D2 แล้วเพิ่มโค้ดนี้ชั่วคราวเพื่อจำลองพัลส์:

```cpp
// ใน setup(): pinMode(3, OUTPUT);
// ใน loop(): ยิงพัลส์สุ่มประมาณ 30 CPM
if (random(0, 1000) < 1) {
  digitalWrite(3, HIGH); delayMicroseconds(50);
  digitalWrite(3, LOW);  delayMicroseconds(300);
}
```

### วิธีทดสอบเส้นทางบลูทูธจริง

ใช้แอป Bluetooth terminal บนมือถืออีกเครื่องส่งบรรทัด `120,1.111,0.0125,2` เข้ามา
วิธีนี้ต่างจากโหมดสาธิตตรงที่ได้ทดสอบการจับคู่และการตัดบรรทัดจาก byte stream ด้วย

## 5. บันทึกการสำรวจและกราฟย้อนหลัง

กราฟบนหน้าหลักแสดงแค่ 5 นาทีล่าสุดและเก็บไว้ในหน่วยความจำ ปิดแอปแล้วหาย
ถ้าต้องเก็บไว้ทำรายงานให้กด **ปุ่มวงกลมแดงบน AppBar** เพื่อเริ่มบันทึก

- ระหว่างบันทึกจะมีแถบแดงบอกเวลาที่ผ่านไป จำนวนจุด และค่าสูงสุด
- ข้อมูลเขียนลงไฟล์ **ทันทีทุกวินาที** ไม่ได้รอจบแล้วเซฟทีเดียว
  ถ้าแบตหมดหรือแอปถูกระบบฆ่ากลางคัน ส่วนที่บันทึกไปแล้วยังอยู่ครบ
- ไอคอนนาฬิกาย้อนเวลาข้าง ๆ = รายการที่บันทึกไว้ทั้งหมด กดเข้าไปดูกราฟทั้งการสำรวจได้
- ในหน้ารายละเอียดมีปุ่มแชร์ ส่งไฟล์ CSV เข้า LINE/อีเมล/Drive ได้เลย

ไฟล์เก็บที่ `Android/data/tools.telepole.telepole_survey_meter/files/telepole_sessions/`
ซึ่งเสียบสาย USB เข้าคอมแล้วลากออกมาได้เลย ไม่ต้องรูทและไม่ต้องขอ permission เพิ่ม
ชื่อไฟล์เป็น `telepole-YYYYMMDD-HHMMSS.csv` เรียงตามเวลาได้ด้วยการเรียงชื่อ

รูปแบบไฟล์ — สามบรรทัดแรกเป็น comment ที่ Excel และ pandas ข้ามได้:

```
# telepole-session v1
# started_at=2026-09-03T14:22:01.123
# cpm_per_usvh=108.00
timestamp,elapsed_s,cpm,cps,usv_h,accumulated_usv
2026-09-03T14:22:02.140,1.0,24.0,1,0.2222,0.00006
```

`cpm` คือค่าดิบจากหลอด ส่วน `usv_h` คำนวณด้วยค่าสอบเทียบ ณ ตอนที่บันทึก
(บันทึกไว้ในหัวไฟล์) ถ้าสอบเทียบใหม่ทีหลัง ไฟล์เก่าไม่เปลี่ยนตาม แต่คำนวณใหม่จาก `cpm` ได้เสมอ

กราฟของการสำรวจยาว ๆ จะย่อจำนวนจุดก่อนวาด โดยเก็บ**ค่าสูงสุด**ของแต่ละช่วง ไม่ใช่ค่าเฉลี่ย
เพราะจุดที่เจอรังสีสูงมักเป็นยอดแหลมสั้น ๆ ตอนกวาดหัววัดผ่าน ถ้าเฉลี่ยจะกลบยอดนั้นหายไป

## 7. หมายเหตุเรื่องแพ็กเกจบลูทูธ

ใช้ `flutter_blue_classic` เพราะแพ็กเกจ SPP ตัวเก่าอย่าง `flutter_bluetooth_serial`
และ fork ของมัน (`flutter_bluetooth_serial_ble`) ยังใช้ `jcenter()` ใน `build.gradle`
ซึ่งถูกถอดออกจาก Gradle 7+ แล้ว ทำให้ build ไม่ผ่านบน toolchain ปัจจุบัน

แพ็กเกจนี้ไม่ประกาศ permission ใด ๆ ใน manifest ของตัวเอง เราจึงต้องประกาศเองทั้งหมด
— สคริปต์ `tool/patch_android.py` ทำให้อัตโนมัติตอน build ใน CI

## 8. Build APK

ทุกครั้งที่ push ขึ้น `main` GitHub Actions จะ build APK ให้อัตโนมัติ
ดาวน์โหลดได้จากแท็บ **Actions** → เลือก run ล่าสุด → ส่วน **Artifacts**

```bash
# หรือดาวน์โหลดผ่าน CLI
gh run download --name telepole-survey-meter-apk
```

APK เซ็นด้วย debug key (Flutter ทำให้อัตโนมัติเมื่อไม่มี keystore) ติดตั้งใช้งานได้ปกติ
แต่อัปโหลดขึ้น Play Store ไม่ได้ ถ้าต้องการก็ต้องสร้าง keystore แล้วเพิ่ม signing config
